## Цель и не цели

- Цель: firmware CH582F+INA228 отдаёт по USB один поток: пары U/I (24 бит), снимки 8 DIO и отдельные UART RX-пакеты; статическая HTTPS-страница (Chrome/Edge Win11, Web Serial) пишет минуту и более, запись независима от просмотра, обзор/zoom/pan, I+U и DIO на общей шкале, UART-журнал, сохранение/открытие записи.
- Не цели: BLE/другие порты, Python/Delphi-развитие, local backend / Python service / Electron; данные не отправляются на сервер. Python-viewer — только историческая наработка. Не переназначать DIO и PA8 LED без разрешения.

## Проверенные на момент консолидации факты (перепроверять)

- Протокол: `[size][cmd]`; `0x3A` = 7 Б/пара (3 Б U, 3 Б signed I, 1 Б DIO); DIO сэмплируется с частотой пар (на втором чтении пары).
- INA228: режим continuous bus+shunt; данные 20-битного АЦП читаются в 24-битных регистрах. Веб-конфигурация по умолчанию использует `pktcnt=20` отдельных чтений, то есть 10 пар на блок.
- Времена преобразования: 50, 84, 150, 280, 540, 1052, 2074, 4120 мкс на канал. Без усреднения два последовательных преобразования по 50 мкс дают теоретически 10k пар/с; по 4120 мкс — около 121 пары/с. 20k отдельных преобразований/с — не 20k пар. **Измерено на Этапе 1** (см. [docs/stage1-baseline.md](docs/stage1-baseline.md)): регистры VBUS/VSHUNT обновляются раз в `2·t_conv`, прошивка читает пару за `2·t_conv`; частоты пар совпали с `1/(2·t_conv)` в пределах 0.1…1.1 % на всех настройках; максимум 9998.6 пар/с (50 мкс, clk 1500 кГц, `to_cnt`=0); 50 мкс отвергается при clk 1300 кГц. Averaging увеличивает период обновления.
- DIO0…DIO7 в коде: **PA4, PA5, PA15, PA14, PA13, PA12, PA11, PA10**; входы с подтяжкой вверх. Не менять порядок. Маска привязана к чтению регистров, не к аппаратно одновременному захвату преобразования; короткие импульсы между отсчётами могут быть пропущены.
- `app_drv_fifo` 2 КиБ, запись атомарная (без частичных блоков); EP1 bulk 64 Б; `USE_SET_LINE_CODING 0` — host baudRate для CDC firmware игнорирует.
- `DEBUG=1`: `DebugInit()` занимает PA8/PA9 под UART1, затем LED занимает PA8; UART1-alt (PB12/13), UART0-alt (PA14/15), UART3 (PA4/5) пересекаются с занятыми сигналами. UART2-alt (PB22/23) также пересекается с PB23 power; при выборе RX проверить конкретный вход, remap и отключение ненужного TX. RX pin не назначать вслепую.
- Ориентир бюджета: 10k пар/с ≈ 70 кБ/с payload + UART 921600 ≈ 92 кБ/с ≈ 162 кБ/с + заголовки; USB FS bulk 64 Б не выглядит узким местом, но гарантий нет.
- Потери возможны **не только** от firmware overflow: баги парсера, disconnect, OS/браузерные паузы. End-to-end гарантии у bulk нет — нужны счётчики/детекция и тесты.
- RAM 32 КиБ (стек 512 Б), приоритеты ISR и размеры FIFO — риски по заголовкам; конкретные решения принимать только по замерам.
- Известные дефекты legacy: `pp.js` (high-byte `init[1]`, пропущенный `await`); O(N)-проход видимого диапазона при децимации и объектные массивы в `wso_ina228+DIO.htm`. Нет Worker, полноценного файла длинной записи и захвата внешнего UART RX; есть CSV-экспорт текущих данных.

## Открытые вопросы (реально блокирующие)

1. UART RX pin: какой физически доступен/разведён на плате (не назначать без подтверждения). Кандидаты без конфликтов по Этапу 1: PA6 (RXD2), PB4 (RXD0), PB20 (RXD3).
2. Доступ к сборке и железу: **закрыт почти полностью** — MounRiver Studio 2 (GCC 8.2.0) и make найдены, плата CH582F+INA228 отвечает на `COM102` (DevID 0x1024, INA228 DID 0x2281), baseline прошит. Открыто: управляемая нагрузка/генератор, источник сигнала на DIO, подтверждение пина UART RX.
3. HTTPS deployment: куда публикуется статика и как обновляется.

Примечание: коды команд и расширение файла записи — не вопросы к пользователю, проектируются в соответствующих этапах. TX не нужен: RX-only подтверждён.

## Согласованные рекомендации (не буквальные требования)

- Компактные TypedArrays/чанки + Worker; multiresolution min/max LOD; viewport без повторного O(N) на redraw.
- Изменения протокола — минимально необходимые, с версией и синхронным parser; `0x3A` сохранять, где возможно; безусловного запрета изменений нет — при необходимости согласовать.
- UART: RX-only; привязка пакета к последней **разобранной** аналоговой точке — условная. Гарантии точности метки нет: задержка включает накопление ring, очереди и USB, особенно на медленных скоростях; период пары нельзя называть точностью метки.
- Если замеры покажут голодание/overrun — рассматривать доработку I2C ISR; заранее ничего не предписывать.
