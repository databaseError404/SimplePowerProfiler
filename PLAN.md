## Цель и не цели

- Цель: firmware CH582F+INA228 отдаёт по USB один поток: пары U/I (24 бит), снимки 8 DIO и отдельные UART RX-пакеты; статическая HTTPS-страница (Chrome/Edge Win11, Web Serial) пишет минуту и более, запись независима от просмотра, обзор/zoom/pan, I+U и DIO на общей шкале, UART-журнал, сохранение/открытие записи.
- Не цели: BLE/другие порты, Python/Delphi-развитие, local backend / Python service / Electron; данные не отправляются на сервер. Python-viewer — только историческая наработка. Не переназначать DIO и PA8 LED без разрешения.

## Проверенные на момент консолидации факты (перепроверять)

- Протокол: `[size][cmd]`; `0x3A` = 7 Б/пара (3 Б U, 3 Б signed I, 1 Б DIO); DIO сэмплируется с частотой пар (на втором чтении пары).
- INA228: режим continuous bus+shunt; данные 20-битного АЦП читаются в 24-битных регистрах. Веб-конфигурация по умолчанию использует `pktcnt=20` отдельных чтений, то есть 10 пар на блок.
- Времена преобразования: 50, 84, 150, 280, 540, 1052, 2074, 4120 мкс на канал. Без усреднения два последовательных преобразования по 50 мкс дают теоретически 10k пар/с; по 4120 мкс — около 121 пары/с. 20k отдельных преобразований/с — не 20k пар. Фактические частоты/корректность пар проверить на стенде (Этап 1); averaging увеличивает период обновления.
- DIO0…DIO7 в коде: **PA4, PA5, PA15, PA14, PA13, PA12, PA11, PA10**; входы с подтяжкой вверх. Не менять порядок. Маска привязана к чтению регистров, не к аппаратно одновременному захвату преобразования; короткие импульсы между отсчётами могут быть пропущены.
- `app_drv_fifo` 2 КиБ, запись атомарная (без частичных блоков); EP1 bulk 64 Б; `USE_SET_LINE_CODING 0` — host baudRate для CDC firmware игнорирует.
- `DEBUG=1`: `DebugInit()` занимает PA8/PA9 под UART1, затем LED занимает PA8; UART1-alt (PB12/13), UART0-alt (PA14/15), UART3 (PA4/5) пересекаются с занятыми сигналами. UART2-alt (PB22/23) также пересекается с PB23 power; при выборе RX проверить конкретный вход, remap и отключение ненужного TX. RX pin не назначать вслепую.
- Ориентир бюджета: 10k пар/с ≈ 70 кБ/с payload + UART 921600 ≈ 92 кБ/с ≈ 162 кБ/с + заголовки; USB FS bulk 64 Б не выглядит узким местом, но гарантий нет.
- Потери возможны **не только** от firmware overflow: баги парсера, disconnect, OS/браузерные паузы. End-to-end гарантии у bulk нет — нужны счётчики/детекция и тесты.
- RAM 32 КиБ (стек 512 Б), приоритеты ISR и размеры FIFO — риски по заголовкам; конкретные решения принимать только по замерам.
- Известные дефекты legacy: `pp.js` (high-byte `init[1]`, пропущенный `await`); O(N)-проход видимого диапазона при децимации и объектные массивы в `wso_ina228+DIO.htm`. Нет Worker, полноценного файла длинной записи и захвата внешнего UART RX; есть CSV-экспорт текущих данных.

## Открытые вопросы (реально блокирующие)

1. UART RX pin: какой физически доступен/разведён на плате (не назначать без подтверждения).
2. Доступ к сборке и железу: MounRiver/тулчейн, плата, генератор/нагрузка для нагрузочных тестов.
3. HTTPS deployment: куда публикуется статика и как обновляется.

Примечание: коды команд и расширение файла записи — не вопросы к пользователю, проектируются в соответствующих этапах. TX не нужен: RX-only подтверждён.

## Согласованные рекомендации (не буквальные требования)

- Компактные TypedArrays/чанки + Worker; multiresolution min/max LOD; viewport без повторного O(N) на redraw.
- Изменения протокола — минимально необходимые, с версией и синхронным parser; `0x3A` сохранять, где возможно; безусловного запрета изменений нет — при необходимости согласовать.
- UART: RX-only; привязка пакета к последней **разобранной** аналоговой точке — условная. Гарантии точности метки нет: задержка включает накопление ring, очереди и USB, особенно на медленных скоростях; период пары нельзя называть точностью метки.
- Если замеры покажут голодание/overrun — рассматривать доработку I2C ISR; заранее ничего не предписывать.

### Этап 2 — DIO/protocol/loss detection/USB robustness (БЕЗ реализации UART)

- [ ] Проверить восемь DIO бегущим битом/всеми масками; закрепить соответствие каждой паре U/I и момент снятия маски.

- [ ] Проверить чётность/границы `pktcnt`, ёмкость выходного блока и обнаружение переполнения кольца измерений; нельзя молча смещать пары U/I/DIO.
- [ ] Loss detection: проверить занятость идентификатора команды (не занимать вслепую); расширение — минимально необходимое, с версией и синхронным parser; `0x3A` сохранять, где возможно.
- [ ] USB robustness: учесть, что потери бывают от parser bug, disconnect, OS/браузерных пауз, а не только от firmware overflow; end-to-end гарантий нет.
- [ ] Тесты: negative signed I / unsigned U, DIO brief pulses, инъекция потерь, disconnect/reconnect.
- **Приёмка:** тесты с артефактами; для `0x3A` — либо подтверждённая совместимость, либо согласованное изменение с версией и обновлённым parser.

### Этап 3 — Web: capture/storage/save-open

- [ ] Статическая страница-рекордер (без сборки, без backend): захват в Worker при поддержке, иначе fallback main + transfer чанков.
- [ ] Инкрементальный парсер, устойчивый к произвольной нарезке USB-чанков (границы внутри заголовка/поля/байта).
- [ ] Хранение: компактные TypedArray-чанки (рекомендация); приём не зависит от рендера. Предусмотреть модель отдельных UART-событий, но реализовывать UART на этапе 5. Детекция потерь — по согласованным счётчикам/версии.
- [ ] Формат файла записи (коды/расширение — проектируются здесь): заголовок с cfg/калибровкой/счётчиками, сохранение и открытие, round-trip.
- [ ] Fake data тесты: fragmentation по 1 байту, signed/unsigned, инъекция потерь; запуск на чистых JS-модулях (`node --test`) + браузерный harness.

Запись не должна незаметно перезаписывать старые данные, как короткий raw-ring. В Network нет запросов с измерениями.

### Этап 4 — Viewport / LOD / DIO

- [ ] LOD-пирамида в Worker (рекомендация: min/max-энвелопа + флаги изменений DIO); инкрементальное построение и фоновая перестройка при открытии файла.
- [ ] Рендер: min/max-конверт, DIO-дорожки и overview; zoom/pan; общая шкала времени; I/U с отдельными шкалами и возможностью наложения. Предусмотреть UART-маркеры для этапа 5. Стоимость кадра зависит от пикселей/LOD, а не длины всей записи.
- [ ] Метрики окна и всей записи; для точных min/max обрабатывать неполные граничные LOD-бакеты. Follow latest включается отдельно; просмотр прошлого не останавливает запись. Прореживание DIO показывает активность, а не усреднённый логический уровень.
- **Приёмка:** экстремумы LOD равны brute-force на тестовых данных со всплесками; DIO-импульс шириной 1 пару виден на overview и точно на zoom; стоимость redraw не растёт с длиной записи (замер 10/30/60 с; отношение ≤ 1,5); FPS — зафиксированное фактическое значение, не обещание.

### Этап 5 — UART RX: ring + mux + журнал text/HEX

- [ ] UART RX-only (8N1, до 921600); ring и дренаж перед USB-отправкой; конкретные объёмы ring/приоритеты ISR — только по замерам (риски по заголовкам учесть).
- [ ] Мультиплексор: UART-дренаж + analog + USB не должны блокировать друг друга; при нехватке места — счётчики/флаги потерь.

- [ ] Привязка UART к последней **разобранной** аналоговой точке — условная, без гарантии точности (накопление/очереди/USB; особенно slow rates); UI помечает приблизительность.
- [ ] Если замеры покажут голодание/overrun — решить по I2C ISR (возможная доработка, не обязательство).
- **Приёмка (код + стенд):** сборка с отчётом RAM; на стенде `rx_overrun/rx_drop` = 0 или зафиксирован порог; порядок байт сохранён; привязка задокументирована как условная. Без лога стенда этап остаётся `[ ]`.
