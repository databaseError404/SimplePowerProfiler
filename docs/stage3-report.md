| Пункт плана | Статус | Артефакт/вывод |
|---|---|---|

**Приёмка:** 5 мин × 10k пар/с на синтетике — 3 млн пар без потерь (0.21 с, 8 Б/пара);
нарезка по 1 байту даёт идентичный датасет; инъекция пропуска определяется по счётчикам;
round-trip идентичен; память и её рост измерены; запись не кольцевая; в Network нет запросов
с измерениями (CSP `connect-src 'none'` + в коде нет fetch/XHR).

## 1. Архитектура

```
recorder.htm  ──  app.js (главный поток)          worker.js (Worker, module)
   UI, статус      navigator.serial (порт)   ──►   parser.js   — инкрементальный разбор [size][cmd]
   кнопки          команды протокола (CFG,         store.js    — PairStore (TypedArray-чанки) + LossTracker
                   FRD, STA, VER)                 recordfile.js — заголовок и формат .pprec
                   байты → postMessage(transfer)  StreamSink  — потоковая запись чанков в файл
```

* **Почему так.** `navigator.serial` есть только в окне (и требует жеста), объект `SerialPort`
  между контекстами не переносится. Поэтому главный поток читает порт и передаёт `ArrayBuffer`
  в Worker без копирования, а вся тяжёлая работа (парсинг, запись в TypedArray, выгрузка чанков
  в файл) идёт вне потока отрисовки — приём не зависит от рендера.
* **CSP страницы:** `default-src 'none'; script-src 'self'; worker-src 'self'; connect-src 'none'`.
  Измерения физически не могут уйти в сеть: в коде нет `fetch`/`XHR`/`WebSocket`, а `connect-src`
  запрещает их на уровне браузера. Данные уходят только в файл через `showSaveFilePicker` или
  скачивание Blob.
* **Опрос счётчиков.** Во время записи страница раз в 2 с посылает `CMD_DEV_STA` (с повтором —
  в Этапе 2 показано, что команды могут теряться при отправке подряд). Счётчики попадают в
  `LossTracker`: оценка пропусков = `(записано + потеряно) × пар_в_блоке − принято`.
  Оценка — **верхняя**: в неё входит конвейерный задел (FIFO прибора + буферы драйвера ≈ 4 КБ,
  это измерено на Этапе 1), поэтому значения меньше ~1000 пар потерей не являются.
* **Ограничения протокола (Этапы 1–2) учтены в UI:** `pktcnt` только чётный и ≤ 34, при 50 мкс
  требуется clk ≥ 1400 кГц, при невыровненном кадре пары не извлекаются (счётчик `misaligned`).

## 2. Формат файла записи (`.pprec`)

```
0            : "PPREC1" (6 Б) — магия и версия формата
6            : u16 headerBytes (LE)
8            : JSON заголовка, добитый нулями до headerBytes (по умолчанию 8192)
8+headerBytes: чанки подряд: u32 count, count×u32 (U24 + DIO в старшем байте), count×i32 (I24 знаковое)
```

Заголовок несёт всё, что нужно для воспроизведения шкал и контроля целостности:
`format/version/created/app`, `device` (DevID/Ver), `cfg` (time_us, clk_khz, pktcnt, mode,
group_bytes, pairs_per_block, pairs_per_s), `calib` (шунт, `k_bus_mv_per_code`,
`k_shunt_ma_per_code`, диапазон VSHUNT), `counts` (пары, блоки, потери, ошибки), `events`
(снимки счётчиков, ошибки, заготовка UART).

Свойства:

* **пишется потоково:** область заголовка резервируется и дописывается при остановке
  (`StreamSink.finish` → `write({type:'write', position:0, ...})`), поэтому длинная запись не
  обязана держаться в памяти;
* **читается без копирования:** чанки становятся `Uint32Array`/`Int32Array` представлениями над
  буфером файла, доступ по индексу — двоичный поиск по чанкам;
* **обрезанный файл не превращается в мусор:** читается корректный префикс (целые чанки целиком,
  из незавершённого — только пары, у которых есть оба значения); тесты это проверяют;
* калибровка в заголовке — важно, потому что в `pp.js` зашит шунт 10 Ом, а на плате стенда 1 Ом
  (Этап 1): файл записи не зависит от констант страницы.

## 3. Тесты

### 3.1 Node (`node --test`, лог `docs/stage3/node-test.log`) — 30/30

| Группа | Что проверяется |
|---|---|
| T2 нарезка | поток 2000 пар: целиком / по 1 байту / случайными кусками → идентичные датасеты |
| T3 знаковость | `U=0xFFFFFF/0x800000` без знака, `I=−0x800000/0x7FFFFF` знаковое |
| выравнивание | нечётный `pktcnt` → кадр помечается, пары из него не извлекаются (за границу кадра парсер не читает) |
| кадры команд | ответы `0x00/0x01/0x03` не мешают данным и распознаются |
| `0x3B` | номера блоков + данные извлекаются (резерв расширения) |
| буфер парсера | рост при большом куске и мелкими чанками — без потерь |
| хранилище | границы чанков, обрезка значений вне диапазона, `parts()` без перевыделения |
| потери | оценка по счётчикам, отсутствие оценки без счётчиков, разрывы `seq`, устойчивость к переполнению списка снимков |
| T7 round-trip | 2500 пар: все пары и поля заголовка совпадают; открытие обрезанного файла (5 долей) — префикс без мусора; обрезка внутри заголовка → понятная ошибка |
| T1 | 3 млн пар (5 мин × 10k пар/с): без потерь, выборочная сверка 500+ пар, время и память |

**T1 (ключевой замер):** 3 000 000 пар обработано за **0.21 с** (≈14 млн пар/с — запас
~1400× к реальному времени), хранилище 46 чанков = **24.1 МБ (8 байт/пара)**, прирост памяти:
буферы +45.6 МиБ (из них ~21 МБ — временные входные буферы, они собираются GC), heap +0.5…2 МиБ.
Рост линейный: 100/200/300/400 тыс. пар → 2/4/5/7 чанков (тест), старые данные не перезаписываются
(отдельный тест на 5 млн пар: первая и последняя пары на месте).

### 3.2 Браузер (`docs/stage3/browser-selftest.log`, headless Chrome) — 16/16

Запуск: `bash tools/stage3/browser_selftest.sh` (поднимает статический сервер, прогоняет
`selftest.htm` и `selftest-worker.htm`, собирает отчёт через `POST /__result`).

* `selftest.htm` — 8 проверок: T2, T3, выравнивание, хранилище, round-trip, заголовок,
  сокращённый T1 (1 млн пар за 0.09 с, 11.5 млн пар/с);
* `selftest-worker.htm` — 8 проверок: Worker как module, init/start/приём потока,
  выдача файла записи, и **прогон реального захвата Этапа 2** (86 040 Б, нарезка по 64 байта,
  как USB): 11 950 пар — ровно столько же, сколько дали парсеры `pp.js` и Python-viewer;
  нет невыровненных кадров, файл открывается, значения в допустимых диапазонах.

Примечание: в headless-режиме с `--virtual-time-budget` таймеры «перематываются» мгновенно, поэтому
harness собирает результаты через HTTP-отчёт, а не через `--dump-dom`; измерение времени в браузере
при виртуальных часах недостоверно (в логе это отмечено).

## 4. Память и её рост (ответ на требование приёмки)

| Длительность при 10 000 пар/с | Пар | Память (8 Б/пара, с округлением чанков) |
|---|---|---|
| 1 мин | 600 000 | 4.6 МБ (9 чанков) |
| 5 мин | 3 000 000 | 24.1 МБ (46 чанков) |
| 30 мин | 18 000 000 | 137 МБ |
| 60 мин | 36 000 000 | 275 МБ |

Чанк — 65 536 пар (512 КиБ), рост без копирования уже принятых данных. Для длинных записей есть
режим **потоковой записи в файл** (`File System Access API`, галочка «писать сразу в файл»): чанки
уходят на диск по мере заполнения, в памяти остаётся незаполненный чанк и счётчики; заголовок
дописывается при остановке. При обрыве записи теряется не более одного незавершённого чанка
(в памяти — не более 512 КиБ).

**Запись не кольцевая:** старые данные не вытесняются; при исчерпании памяти браузер аварийно
завершит вкладку, а не «затрёт» начало — это проверено тестом на 5 млн пар (первая пара на месте).

## 5. Что осталось / ограничения

1. **Прогон с реальным прибором в браузере** — не выполнялся: `navigator.serial.requestPort()`
   требует жеста пользователя, в headless это невозможно. Процедура для пользователя:
   ```bash
   node tools/stage3/serve.mjs          # http://localhost:8765/recorder/recorder.htm
   ```
   затем «Подключить» → выбрать COM-порт прибора → «Начать запись» → «Остановить» → «Сохранить файл»;
   ожидаемо: при 84 мкс ≈ 5952 пар/с, при 50 мкс/1500 кГц ≈ 10 000 пар/с, счётчики без роста.
2. **Потоковая запись в файл** реализована, но не проверена с прибором (нужен тот же жест).
3. **Графики, LOD, zoom/pan** — Этап 4 (файл и чанки для этого уже готовы: `RecordFile.toStore()`
   отдаёт те же чанки).
4. **UART-события** — Этап 5: в формате и в хранилище есть место (`events`), реализация не начата.
5. Точная детекция пропусков возможна только после расширения протокола (`0x3B` с `seq` или
   счётчик перезаписи кольца) — проект в `docs/stage2-report.md`, раздел 4; сейчас оценка
   по счётчикам — верхняя граница.
