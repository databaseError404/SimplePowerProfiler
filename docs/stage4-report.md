## 1. LOD-пирамида (`lod.js`)

* Уровень 0 — бакеты по 64 пары, уровень k — по `64·2^k`; максимум 12 уровней (бакет до 131 072 пар).
* На бакет: `minU`, `maxU`, `minI`, `maxI`, `dioOr` (линии, которые были активны), `dioAnd`
  (линии, которые держались высокими), `dioChanges` (число смен маски) — 19 байт на бакет.
* Память: 84 КиБ на 10 с записи (100 тыс. пар), 672 КиБ на 60 с (600 тыс. пар) ≈ **1,15 байта на пару**
  (14 % от сырых 8 байт/пара).
* Стоимость сборки: **0,33…0,38 мс на 1000 пар** (600 тыс. пар — 228 мс), то есть пирамида строится
  в 250 раз быстрее реального времени; при записи 10 000 пар/с это ~3 % времени кадра.
* Инкрементальная сборка (разные порции) побитово совпадает с полной пересборкой — тест.
* Новый уровень создаётся, когда у верхнего уровня завершается первый бакет, и его агрегат собирается
  из двух готовых дочерних бакетов, поэтому данные не теряются.

### Семантика счётчика смен DIO

Смена считается на паре `k`, если `mask(k) != mask(k-1)`; для диапазона, начинающегося не с нуля,
«предыдущей» берётся пара `from-1`. Такая семантика позволяет **суммировать** счётчики по уровням и
по участкам окна без потери смен на границах. Регресс-тест: маска меняется ровно на границах бакетов
(каждые 64 пары) — счётчики бакетов и brute-force совпадают.

## 2. Метрики (`metrics.js`)

* `windowExtrema(pyramid, source, from, to)` — точные min/max и активность DIO: середина берётся из
  бакетов, целиком попавших в окно, а **неполные граничные бакеты дочитываются по сырым парам**
  (требование плана) — результат совпадает с brute-force при любой длине записи (проверено на 8 окнах,
  включая окна внутри одного бакета и на его границе).
* `windowMetrics(..., {withAvg: true})` — средние U/I считаются по сырым парам и только по запросу
  (галочка «считать средние в окне»); в пирамиде средних нет, и это честно отражено в интерфейсе.
* `recordMetrics` — метрики всей записи по верхнему уровню пирамиды + перевод в мВ/мА по калибровке
  из заголовка файла (шунт 1 Ом → `k_shunt_ma_per_code = 1,953125e-5`).

## 3. Рендер и взаимодействие (`render.js`, `viewport.js`, `worker.js`)

* Раскладка: графики U/I (0…62 % высоты), 8 дорожек DIO (62…86 %), обзор всей записи (88…100 %).
* Энвелопа: по колонкам рисуются вертикальные отрезки min…max; U и I — раздельные шкалы
  (мВ/мА, подписи диапазона) либо наложение на общую шкалу (галочка).
* DIO: при прореживании — «активность» (полутон — линия была высокой, ярче — менялась, сплошная — держалась),
  при зуме до ≤ 1 пары на колонку — точные уровни ступеньками.
* Обзор: отдельная полоса с рамкой текущего окна; по клику/двойному клику — «показать всё».
* Взаимодействие: колесо — зум к курсору, перетаскивание — сдвиг (при этом follow выключается),
  кнопки «+»/«−»/«Всё», курсор показывает точные значения пары (U в мВ, I в мА, маска DIO).
* `followLatest` — отдельный переключатель: при включении окно едет за новыми данными; при просмотре
  прошлого новые данные продолжают приниматься (запись в Worker не зависит от отрисовки).
* Маркеры событий: `renderer.events` — вертикальные метки по времени (сейчас снимки счётчиков и ошибки;
  UART-пакеты добавятся на Этапе 5 без изменения API).

### Почему рендер в Worker

Данные (PairStore + пирамида) живут в Worker, поэтому рисование идёт там же в `OffscreenCanvas`,
а главный поток получает готовый `ImageBitmap`. Это исключает копирование данных в UI-поток и
гарантирует, что приём не зависит от рендера. Требуется поддержка `OffscreenCanvas` (Chrome/Edge);
если её нет, воркер сообщает об этом (`caps.offscreen`), и данные всё равно пишутся.

## 5. Исправления по замечаниям пользователя (после первого просмотра)

Пользователь открыл запись в браузере и сообщил две проблемы; обе разобраны по скриншотам
(пиксельный анализ PNG в `D:6\PowerProfiler`) и исправлены.

### 5.1 «График DIO при 1 состоит из зубцов»

**Что было.** Профиль дорожки D3 в скриншоте: `0 0 0 0 2 0 0 0 0 0 2 0 …` — короткий тик каждые
6 колонок. Две причины:

1. `dioChanges` в пирамиде считался по **всей маске**, а не по линии: когда переключалась любая
   другая линия, колонка помечалась как «активность», и ровный уровень этой линии рисовался
   короткой меткой вместо линии;
2. в точном режиме при сильном зуме (несколько колонок на одну пару) заполнялась только каждая
   N-я колонка, а остальные оставались нулевыми — уровень чередовался «1 / 0» и выглядел как зубцы.

**Что сделано.**

* в LOD добавлена побитовая маска `dioChangedMask` (какие именно линии менялись внутри бакета);
  она же отдаётся в колонках (`buildColumns`);
* дорожки DIO рисуются как в логическом анализаторе: ровный уровень — линия (даже если в колонке
  менялись другие линии), метка активности — только там, где менялась **эта** линия;
* в точном режиме (≤ 1 пары на колонку) рисуется настоящий уровень по `dioExact` (меток нет);
* раскладка колонок в точном режиме исправлена: пара заполняет все колонки, которые занимает.

**Регресс-тесты:** Node — «ровная линия не дробится, если меняются другие линии» (4 масштаба),
«импульс в одну пару помечается активностью»; браузер — **пиксельная** проверка: ровная линия D3
при трёх масштабах даёт постоянную высоту и верхнюю строку (получено: высота 2…2 px, верх 0…0 px).

### 5.2 «Графики тока и напряжения попадают друг в друга»

**Что было.** U и I рисовались в одной области с разными шкалами; при широком размахе линии
схлопывались и визуально сливались (в скриншоте: U — 39 281 пиксель, I — 1 142 пикселя,
перекрытие по строкам 218 px).

**Что сделано.**

* по умолчанию **две отдельные панели**: U сверху (0…30 % высоты), I снизу (33…62 %); проверено
  пиксельно: нижняя строка U выше верхней строки I (130 против 157 в тесте);
* режим наложения («наложить U и I») остался как опция — одна панель с общей шкалой;
* шкалы отображения стали **устойчивыми**: используются квантили 0,5 % и 99,5 % вместо абсолютных
  min/max, поэтому одиночный выброс (сбойное чтение) больше не «схлопывает» полезный сигнал в линию;
  при обрезке выводится предупреждение с полным диапазоном, а точные min/max остаются в метриках.

**Регресс-тесты:** Node — «одиночный выброс не схлопывает сигнал (квантили)» (проверяется и флаг
`clipped`, и сохранение полного диапазона), «режим наложения даёт общую шкалу»; браузер — пиксельная
проверка «U и I разнесены по панелям».

### 5.3 «Графики очень мелкие, лучше на одной панели» (второй заход)

**Что было.** Две отдельные панели делили область графика, и на низком окне каждый след получал
~120 px высоты; осей значений и времени не было вообще (только подпись «U a…b мВ»), поэтому
положение графика не с чем было соотнести, а тонкая линия на пустом поле выглядела «странно».

**Что сделано.**

* **одна панель** с двумя внутренними полосами (U сверху, I снизу) и разделителем — визуально один
  график, но следы не накладываются; режим «наложить U и I» остался отдельной галочкой;
* **высота канвы** — `clamp(420px, 58vh, 760px)` вместо фиксированных 460 px: на окне 1400 px
  канва 1554×759, полоса U 0…231 px, полоса I 262…501 px — то есть **~235 px на след** вместо ~120;
* **сетка значений с подписями** (5 горизонталей в каждой полосе, значения в мВ/мА справа) —
  теперь видно, на каком уровне находится сигнал;
* **ось времени** — подписи секунд в разделителе полос и лёгкие вертикали по панели (шаг
  подбирается автоматически: от 1 мс до 5 мин);
* следы стали заметнее: края min/max — линиями 1,4 px, размах — полупрозрачной полосой (alpha 0.4);
* страница **`demo-view.htm`** — синтетическая запись (шум, «лестница» нагрузки, импульс DIO в одну
  пару) с пресетами «вся запись / 1 с / 100 мс / к импульсу»: вид графиков можно проверять без прибора;
  на странице рекордера то же самое доступно кнопкой «Демо-данные» или параметром `?demo=1`.

**Проверено пиксельно** (скриншот `demo-view.htm` 1554×759, анализ по цветам):

| Область | Пиксели U | Пиксели I | Пиксели DIO | Заполнение полосы |
|---|---|---|---|---|
| полоса U (0…231) | 68 352 | 0 | 0 | **93 %** |
| разделитель/ось (247) | 0 | 0 | 0 | — |
| полоса I (262…501) | 0 | 25 613 | 0 | **86 %** |
| дорожки DIO (516…668) | 0 | 0 | 12 457 | — |
| обзор (687…759) | — | — | — | — |

То есть следы занимают почти всю свою полосу (были тонкие линии на пустом поле), и полосы не
пересекаются.

**Стоимость (Node, чистые модули):** `buildColumns` на 1554 колонки и 50 тыс. пар — **1,47 мс**,
`computeScales` — **0,12 мс**, `dioLaneModel` ×8 — **0,08 мс**, обзор — **0,05 мс**. Остальное время
кадра — растеризация canvas: в headless с программным рендером ~30 мс на канве 1554×759
(≈28 кадр/с), в обычном окне с GPU-ускорением существенно меньше; в harness (канва 1200×460)
измерено **8,8 мс/кадр → 114 кадр/с**.

Попутно исправлено:

* **потерянная инициализация воркера** (при переписывании `app.js` для Этапа 4 строка `init` осталась
  только в «Начать запись») — из-за этого просмотр открытого файла и демо-данных не запускались;
  теперь `init` отправляется при загрузке страницы и повторно при старте записи;
* **квантили для шкал**: вариант через гистограмму «размывал» диапазон при одиночном выбросе
  (тест это поймал) — заменён на quickselect (точно и O(n));
* в `worker.js` добавлена команда `demo` (синтетическая запись), в интерфейс — кнопка «Демо-данные».

### 5.4 «Горизонтальные полки, которых не должно быть» (третий заход)

**Что показал пиксельный разбор `Screenshot_4.png`:**

* в полосах U и I длинных горизонтальных участков следа **нет** (проверено поиском одноцветных пробегов
  > 150 px: 0 в U, 0 в I) — «полками» выглядели **дорожки DIO**: в области DIO нашлось 21 длинная
  горизонтальная линия и сплошные зелёные блоки на всю ширину;
* причина блоков: метка активности рисовалась полосой в 76 % высоты дорожки, а при частых
  переключениях (или шумящих входах) активность есть почти в каждой колонке → дорожки сливались
  в сплошные полосы, уровень линии в них не читался;
* следы U/I при шумном сигнале рисовались как min/max-энвелопа (сплошная заливка), поэтому
  выглядели «странно»: сплошное поле с вертикальными штрихами вместо привычной линии сигнала.

**Что сделано.**

* **Главный след — линия среднего.** В LOD добавлены `meanU`/`meanI` (целочисленное «бегущее» среднее
  на бакет, +8 байт на бакет), в колонках — взвешенное среднее. График теперь рисует: тонкую
  полупрозрачную полосу размаха (alpha 0.16) + **линию среднего 1,5 px** — как обычный график;
* **метки активности DIO** — тонкая чёрточка (32 % высоты дорожки, в середине) вместо полосы
  во всю высоту: уровень линии виден, а активность не превращается в сплошной блок;
* сетка значений чуть заметнее (alpha 0.10), чтобы читалась как сетка, а не как артефакт.

**Проверено:**

* карта канвы (ASCII по цветам) после правок: следы U и I — тонкие линии со «ступеньками» нагрузки,
  заливки нет; дорожки DIO — тонкие линии уровней (медиана 2 px) с редкими метками активности
  (D4/D6 — ровные линии 1 px, D5 — 225 колонок активности из 1551);
* новый тест: среднее в колонке отличается от brute-force не более чем на 5 кодов (≈1 мВ при 3.3 В —
  целочисленное «бегущее» среднее без накопления суммы), среднее всегда внутри размаха, размах
  присутствует более чем в половине колонок;
* все наборы: **51 тест Node**, **26 проверок в браузере**, стоимость кадра от длины записи
  по-прежнему не зависит (отношение 1,00).

### 5.5 «Точки реальных отсчётов и соединяющие линии» (четвёртый заход)

**Что показал разбор `Screenshot_5.png`** (кроп только графиков U и I): в полосах найдены **сплошные
горизонтальные линии полной ширины** (8 штук, цвета `#242629`/`#2c3035` — это была сетка значений)
и след из длинных плоских участков. Сетка читалась как часть данных, а след не показывал отдельные
отсчёты.

**Что сделано.**

* **Точки отсчётов + соединяющая линия.** Главный след рисуется линией среднего, а поверх — маркеры
  реальных отсчётов. Точки показываются, когда между отсчётами есть место по горизонтали
  (`step ≤ 0,34` пары на колонку, то есть ≥ 3 px между точками): 3×3 px при разрежении ≥ 10 px,
  иначе 3×3/2×2. При плотном зуме точки не рисуются — там сама линия и есть последовательность
  отсчётов.
* **Сетка стала точечной** (штрихи 2 px с шагом 6 px, alpha 0.10) — её больше нельзя спутать
  со следом; при желании отключается галочкой «сетка значений».
* **Индикатор вида** в панели: «точки отсчётов (1 пара = N px)» / «точный (1 пара/колонка)» /
  «прорежено: N пар/колонка» — видно, показываются ли отдельные отсчёты или агрегат.
* Новые галочки в интерфейсе: **точки отсчётов**, **размах (шум)**, **сетка значений**;
  в демо-странице те же переключатели.

**Проверено пиксельно** (`demo-view.htm`, канва 1556×761):

| Что | Результат |
|---|---|
| Точки отсчётов | на зуме (6 px между отсчётами) видны отдельные маркеры с линией между ними (паттерн `U.U.U..U.U.UU` при выборке через пиксель) |
| След U | 60 476 пикселей на 1555 колонках (непрерывный след по всей ширине) |
| Сетка | штриховая, в пробеги следа не попадает (в полосе I длинных одноцветных пробегов следа — 0) |
| Плоские участки | 66 участков по ~249 px в полосе U — это **данные демо-записи**: «лестница» нагрузки держит ступень 0,4 с = 2000 пар = 62 колонки |

Последнее важно: ровные участки появляются там, где сигнал действительно не меняется (или где
нагрузка переключается ступенями). Если такие участки видны там, где сигнал должен меняться —
это уже вопрос к данным/настройкам измерения, и разбирать его нужно по конкретному скриншоту
с указанием, в каком месте записи это видно.

## 6. Что осталось / ограничения

1. **Прогон с прибором в браузере** — по-прежнему требует жеста пользователя (как в Этапе 3):
   `node tools/stage3/serve.mjs` → `http://localhost:8765/recorder/recorder.htm`.
   Ожидаемо: 5952 пар/с при 84 мкс, 10 000 пар/с при 50 мкс/1500 кГц, кадр ~2–4 мс.
2. **Живой просмотр во время записи** держит данные в Worker (8 байт/пара + ~1,15 байта/пара LOD).
   Для длинных записей рекомендуется режим «писать сразу в файл» — но тогда просмотр доступен только
   по уже записанной части в памяти; чтение из файла на лету не реализовано (кандидат в Этап 6).
3. **UART-маркеры** — API готов (`renderer.events`), наполнение — Этап 5.
4. **Кнопки/жесты** не проверялись в ручном режиме (headless не умеет ввод): зум/пан/курсор проверены
   на уровне математики (`viewport.js`) и отрисовки, но не «руками» в окне.
5. Точная детекция пропусков по-прежнему возможна только после расширения протокола (проект Этапа 2).
