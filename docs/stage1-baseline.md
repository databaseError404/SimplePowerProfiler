### 3.4 Пары U/I и циклы преобразования (темп обновления ADC)

Метод (скрипт `measure_pairs.py --dupe-check`/`--adc-ct`): оба чтения группы нацелены на один и тот же
регистр (`rd[0] = rd[1]`), поэтому в потоке нет U/I, а есть повторные чтения одного регистра. Период
между соседними значениями в потоке = `2·P` (группа = 2 чтения по `P` мкс). Если ADC обновляет регистр
раз в `A` мкс, то доля совпадающих подряд значений описывается моделью
`dup = 1 − (2P/A)·(1−q)` при `2P ≤ A` и `dup = q` при `2P > A`, где `q` — собственная повторяемость
значений сигнала (измеряется на больших `P`, когда все выборки независимы; теоретически `q = Σp²` по
распределению значений — совпало с измеренным).

Измерения (clk = 2000 кГц, pktcnt = 20, окно 3 с, лог `docs/stage1/measure-adc-cadence.log`):

| CT INA228 | `P`, мкс | доля повторов | `q` | оценка `A` | ожидание `2·t_conv` |
|---|---|---|---|---|---|
| индекс 1 (84 мкс) | 40 / 50 / 60 / 70 / 80 | 62.1 / 52.7 / 43.4 / 34.4 / 25.4 % | 21 % | 167…169 мкс | 168 мкс ✔ |
| индекс 1 (84 мкс) | 90…600 | 21…24 % (выход на `q`) | 21 % | — | 168 мкс ✔ |
| индекс 5 (1052 мкс) | 100 / 300 / 600 / 1052 | 91.1 / 72.9 / 46.5 / 5.2 % | 5.4 % | 2094…2127 мкс | 2104 мкс ✔ |
| индекс 5 (1052 мкс) | 1400 | 5.6 % (выход на `q`) | 5.5 % | — | 2104 мкс ✔ |

Оценка `A` совпала с `2·t_conv` с разбросом ±1.5 % на двух разных настройках (84 и 1052 мкс), то есть
на 12-кратном диапазоне.

Повторно **на прошитом baseline** (лог `docs/stage1/measure-adc-cadence-flashed.log`): доля повторов
61.9 % (CT=1, P=40), 22.0 % (CT=1, P=84), 91.0 % (CT=5, P=100), 4.8 % (CT=5, P=1052) — совпадает
с оценками выше в пределах 1 п.п.

Следствия (подтверждают пункты плана):

* INA228 в режиме continuous bus+shunt обновляет **каждый** из регистров VBUS/VSHUNT раз в `2·t_conv`;
* прошивка читает один регистр за такт таймера (ISR `TMR1_IRQHandler`), т.е. пару — за `2·t_conv`,
  поэтому частота пар = `1/(2·t_conv)` и никакие обновления не теряются и не дублируются:
  при `P = t_conv` доля повторов в точности равна `q`, то есть каждое чтение приходится на новое
  обновление (фаза чтения относительно ADC может медленно дрейфовать, но систематического
  пропуска/дублирования нет);
* **U и I внутри пары всегда из разных циклов**: `rd[0] = VBUS`, `rd[1] = VSHUNT`, чтения идут
  последовательно через `t_conv`, то есть I в паре измерен на `t_conv` позже U. Это систематический
  сдвиг (на 50 мкс — 50 мкс, на 4120 мкс — 4.12 мс), а не «смешивание» значений: каждое из них свежее;
* устаревшая таблица «RDY 2 channel» в комментарии `cmd_decode.c` (188/248/379/640/1160/1400/2431/8326 мкс)
  измеренному темпу `2·t_conv` **не соответствует** и как ориентир не годится.

### 3.5 Потери на максимальной частоте

* При 10 000 пар/с (70 кБ/с payload) счётчик `to_cnt` (`CMD_DEV_STA`) = **0** во всех прогонах.
* Разница «пар по счётчику прибора» и «принято хостом» постоянна: **570 пар (57 блоков ≈ 4.1 кБ)**
  и не зависит от длины окна (6 с и 30 с дают одинаковые 570 пар) — это конвейерный буфер
  (FIFO 2048 Б + буферы драйвера/USB), а не пропорциональная потеря. При пропорциональной потере
  0.55 % на 30-секундном окне разница была бы ≈1765 пар.
* Наблюдение (важно для Этапа 2): при высоком потоке ответ на команду иногда не приходит —
  `DevEP1_OUT_Deal()` отбрасывает принятый пакет, если `app_cmd_len != 0` (приём без очереди команд).
  В скрипте измерения добавлены повторы; при отладке это выглядело как «нет ответа на `CMD_DEV_STA`».

### 3.6 Наблюдаемые значения U/I (нагрузка ещё не подключена)

Шунт платы подтверждён пользователем: **1 Ом**. В `pp.js` зашито 10 Ом (`INA228rShunt` — константа платы
автора), поэтому шкала мА в веб-интерфейсе для этой платы **занижена в 10 раз**. Пересчёт:
1 LSB 20-битного VSHUNT = 312.5 нВ, код 24-битного регистра = LSB/16, поэтому
`I[мА] = raw · 1.953125e-5 / R[Ом]`; полная шкала при 1 Ом — **±163.84 мА** (CONFIG bit4 = 0,
диапазон ±163.84 мВ). В `measure_pairs.py` добавлен параметр `--shunt-ohm` (по умолчанию 1).

Измерено на 84 мкс (окно 5 с, `--shunt-ohm 1`), нагрузка **не подключена**:

| Величина | Значение |
|---|---|
| U | 3281.2…3318.9 мВ (размах 37.7 мВ) |
| I | −0.0294…+0.0366 мА (размах 0.066 мА) — десятки мкА шума/утечки без нагрузки |

Проверка min/max на **известной** нагрузке остаётся открытой: пользователь нагрузку пока не подключает.
Абсолютная точность не подтверждена (калибровка платы не измерялась); калибровочные константы должны
попасть в конфигурацию записи на Этапе 3, а не оставаться в коде страницы.

Наблюдение для Этапа 2: DIO-байт во всех парах стабильно **`0xD7`** = `0b1101_0111`: высокие
DIO0 (PA4), DIO1 (PA5), DIO2 (PA15), DIO4 (PA13), DIO6 (PA11), DIO7 (PA10); низкие — **DIO3 (PA14)**
и **DIO5 (PA12)**. При подтяжках вверх (`IN_PU`) на свободных входах ожидалось бы `0xFF`, поэтому два
пина явно нагружены/притянуты вниз вне прошивки (внешние подтяжки, подключённый DUT или разводка платы).
Наблюдение **сохранилось и после прошивки baseline**, поэтому это не артефакт версии прошивки.
Проверка DIO управляемым сигналом — Этап 2 (тест B2/T4).

> Примечание: в первой редакции этого отчёта было записано «`DIO = 0x01`» — это была ошибка чтения
> вывода скрипта («масок 1» — количество различных масок, а не значение). Скрипт поправлен: теперь он
> печатает сами маски (`маски 0xD7`).

## 4. Риски по заголовкам: RAM, приоритеты ISR, размеры FIFO

### 4.1 RAM (32 КиБ, стек 512 Б в `Ld/Link.ld`)

| Регион/буфер | Размер, Б | Комментарий |
|---|---|---|
| `.highcode` (код в RAM) | 5244 | весь `USE_RAM_CODE=1`: `Main_Circulation`, `USBSendData`, ISR, `I2CBus*` |
| `.data` | 124 | |
| `.bss` | 4184 | включая буферы ниже |
| `.stack` | 512 | закреплён в конце RAM (`ORIGIN+32K−512`), отдельно от `.bss` |
| `i2c_dev` | 1288 | `i2c_buf[256]` uint32 = 1024 + `i2c_dio_buf[256]` = 256 + служебное |
| `app_tx_buffer` (USB TX FIFO) | 2048 | `APP_TX_BUFFER_LENGTH = 1<<11` |
| `send_pkt` | 234 | `DLE_DATA_SIZE = 234` |
| `EP0_Databuf` / `EP1_Databuf` | 192 / 128 | по 64 Б на направление |
| `i2c_blk` | 122 | **см. риск 4.4** |
| `cfg_i2c` / `app_cmd_buf` | 64 / 64 | |
| **Свободно** | **≈ 22 704** | между `_ebss` (0x20002550) и стеком (0x20007E00) — запас под будущие буферы UART/счётчики |

Занято по отчёту линкера: 10 064 Б из 32 КиБ (30.71 %), Flash 15 368 Б из 448 КиБ (3.35 %).

### 4.2 Приоритеты ISR

* `PFIC_SetPriority`/`NVIC_SetPriority` в проекте **не вызываются** — все прерывания на приоритете по
  умолчанию (0). Вложенности между ними нет; при равных приоритетах первым обслуживается IRQ с меньшим
  номером: **USB_IRQn = 22 обслуживается раньше TMR1_IRQn = 24**.
* `TMR1_IRQHandler` выполняет полный I2C-обмен (`I2CBusRead24bits`, busy-wait до 100 мкс) — при 50 мкс
  периода это основная нагрузка CPU; длинный ISR задерживает USB, но не прерывается им (равные приоритеты).
* SysTick используется только как счётчик (`SysTick->CTLR = 5`), прерываний не генерирует.
  От него зависят `sleep_us()` и таймаут I2C в `i2c_wait_status` (`FREQ_SYS/10000` тиков). База времени
  SysTick (1 тик = 1/FREQ_SYS или 1/(FREQ_SYS/8)) по документации на CH583 однозначно не подтверждена;
  косвенная проверка через round-trip команды не разрешилась (латентность хоста ≈63 мс маскирует
  разницу в доли мс). Это не влияет на измеренные частоты пар: они задаются таймером TMR1
  (`R32_TMR1_CNT_END = (FREQ_SYS/1000000)*period_us`) и подтверждены измерением (3.2).

### 4.3 FIFO и счётчики

* `app_drv_fifo` — 2048 Б, запись блока **атомарная** (`app_drv_fifo_write`): при нехватке места блок
  отбрасывается целиком (10 пар сразу), частичных блоков не бывает.
* `status.all_read_count` / `all_overflow_cnt` считают **блоки**, а не пары; `CMD_DEV_STA` отдаёт их как
  `rd_cnt` / `to_cnt`. Пары = `rd_cnt × pktcnt/2`. Имена полей вводят в заблуждение.
* EP1 bulk = 64 Б (`MAX_TX_PACKET_SIZE`), блок 72 Б отправляется как 64 + 8; после ровно 64 Б
  отправляется ZLP (`old_send_len == MAX_TX_PACKET_SIZE`).
* Ошибки/таймауты I2C в `TMR1_IRQHandler` **не проверяются** (`ret` игнорируется, счётчика нет):
  при сбое чтения в кольцо попадёт частично записанное/старое значение — детекции нет.

### 4.4 Ёмкость выходного блока (`i2c_blk`) — потенциальное переполнение

`i2c_blk.data` — `uint16_t[60]` = **120 Б**, а в 24-битном режиме заполняется
`count = raw_count*3 + raw_count/2` байт. Отсюда:

| pktcnt (24 бита) | `count`, Б | Итог |
|---|---|---|
| 20 (значение из `pp.js` и `ina228_start()`) | 70 | норма |
| 34 | 119 | предел |
| **35…40** | 122…140 | **выход за `i2c_blk`** на 2…20 Б: затираются `i2c_dev.raddr`, `timer_flg`, `i2c_buf_rd/wr`, `i2c_rd_24bit` |

`MAX_I2C_PKTCNT24 = 40` ограничивает pktcnt сверху, но не по ёмкости буфера, поэтому `pktcnt ≥ 35`
формально разрешён и разрушает состояние драйвера. Проверять это на стенде — Этап 2
(потребуется готовность перезапустить прибор по питанию). Сейчас код не менялся.

### 4.5 Прочие риски, зафиксированные по коду

* **Чётность `pktcnt`.** DIO-байт добавляется к каждому второму чтению внутри блока
  (`if((n & 1) != 0)`), а пары в потоке задаются порядком `rd[0]=VBUS, rd[1]=VSHUNT`. При нечётном
  `pktcnt` граница блока разрывает пару: в следующем блоке «U» и «I» окажутся переставленными, а DIO
  привяжется к другому чтению. `pp.js` шлёт `pktcnt = 20` (чётное), поэтому дефект не проявляется.
* **Блокирующий PRINT в основном цикле.** `PRINT("CMD: Out buffer overflow!\r\n")` при переполнении
  TX FIFO пишет в UART1 на 115200 (≈87 мкс на символ, ≈2.4 мс на строку) и блокирует основной цикл —
  то есть усугубляет переполнение. `DEBUG_USB`/`DEBUG_I2C` = 0, в горячем пути других печатей нет.
* **Потеря команд.** Приём команд без очереди (см. 3.5): пакет отбрасывается, если предыдущий ещё не
  обработан. `USE_SET_LINE_CODING = 0` — baudRate от хоста игнорируется, но `SET_CONTROL_LINE_STATE`
  превращается в `CMD_I2C_PWR` (DTR: 1 = включить питание INA228, 0 = выключить).
* **ALERT/CR не используется.** `DIAG_ALRT` (0x0b) настраивается на «conversion ready» (`0x4000`), но пин
  ALERT прошивкой не читается, и таймер чтения не синхронизирован с ADC (свободная фаза) — при изменении
  `time` фаза чтения относительно преобразования произвольна (на частоту пар это не влияет).
* **`pp.js`: `init[1]` (DIAG_ALRT) отправляется с чужим старшим байтом** — `blk[15] = (cfg.init[0][2] >> 8)`
  вместо `init[1][2]`, из-за чего в регистр 0x0b уходит `0xC040` вместо `0x4000` (устанавливается бит 15,
  ALATCH). Для этой прошивки безвредно (ALERT не читается), но это дефект.
* **`pp.js`: `SetINA228Speed()` не обновляет `clk_khz`** (остаётся 1300 кГц), поэтому выбор «20000 SPS»
  в интерфейсе приводит к отказу конфигурации и остановке измерения (подтверждено на стенде, см. 3.3).
* **`pp.js`: шунт 10 Ом вместо 1 Ом на этой плате** — `config_ina228.rShunt = 10.0` и
  `kShunt = 0.0000019613524`, поэтому отображаемые мА в 10 раз меньше фактических (см. 3.6).
  Это не «ошибка» (константа платы автора), но для нашей платы шкала неверна; калибровка должна быть
  частью конфигурации записи (Этап 3), а не кода страницы.
* **Ориентир `162 кБ/с`** из плана не проверялся: измеренный максимум только U/I-потока — 70 кБ/с
  payload (72 кБ/с с заголовками). UART-часть — Этап 5.
* **Латентность команд от хоста.** Через pyserial/usbser round-trip команды (медиана 10 запросов)
  ≈ 63 мс, разброс 1…2 мс, разница между валидным и несуществующим адресом I2C ≈ 0.5 мс. Это
  латентность хостовой части (драйвер/опрос), а не ограничение потока: поток 10 000 пар/с
  принимается полностью. Для Этапа 3 (Web Serial) латентность команды нужно измерить отдельно.

## 5. Воспроизводимый сценарий замеров (для повторения)

```bash
# 0) Прошивка baseline (нужен WCH-LinkE на SDI: TIO=PB14, TCK=PB15, 3V3, GND)
bash tools/stage1/flash_baseline.sh --check      # проверить Link и диапазон образа
bash tools/stage1/flash_baseline.sh --yes        # прошить build/stage1/I2C2USB/obj/I2C2USB.hex

# 1) Baseline-сборка (out-of-tree, не трогает исходники и obj/)
bash tools/stage1/build_baseline.sh
#    варианты: GCC_FLAVOR=gcc12|gcc15, MR_ROOT=..., BUILD_ROOT=..., NO_CLEAN=1
#    результат: build/stage1/build.log + build/stage1/I2C2USB/obj/I2C2USB.{elf,bin,hex,map,lst}

# 2) Проверка прибора (только чтение версии/идентификаторов)
python tools/stage1/measure_pairs.py --list
python tools/stage1/measure_pairs.py --port COM102 --probe

# 3) Частоты пар: весь диапазон conversion time (по 5 с на настройку)
python tools/stage1/measure_pairs.py --port COM102 --sweep --seconds 5 --clk 1300 --pktcnt 20

# 4) Максимум: 50 мкс (нужен clk >= 1400 кГц), 30 с
python tools/stage1/measure_pairs.py --port COM102 --time 50 --clk 1500 --seconds 30 --drain 2

# 5) Темп обновления регистров ADC (доказательство сдвига U/I на t_conv):
#    оба чтения группы -> один регистр, период чтения и индекс CT задаются раздельно
python tools/stage1/measure_pairs.py --port COM102 --dupe-check --adc-ct 1 --time 40  --clk 2000 --seconds 3
python tools/stage1/measure_pairs.py --port COM102 --dupe-check --adc-ct 1 --time 84  --clk 2000 --seconds 3
python tools/stage1/measure_pairs.py --port COM102 --dupe-check --adc-ct 5 --time 100 --clk 2000 --seconds 3
python tools/stage1/measure_pairs.py --port COM102 --dupe-check --adc-ct 5 --time 1052 --clk 2000 --seconds 3
#    ожидание: доля повторов ~62 % при (CT=1, time=40), ~21 % при (CT=1, time>=84),
#               ~91 % при (CT=5, time=100), ~5 % при (CT=5, time>=1052)

# 6) Корректность пар на ступеньке нагрузки: запись пар в CSV + анализ сдвига
#    (--shunt-ohm 1 — шунт платы; в pp.js зашито 10 Ом)
python tools/stage1/measure_pairs.py --port COM102 --time 84 --seconds 5 --csv pairs.csv --shunt-ohm 1
python tools/stage1/analyze_skew.py pairs.csv --time 84 --shunt-ohm 1 --threshold-mv 3.0
```

Скрипт измерения только запускает/останавливает штатное измерение; формат `0x3A` не меняет, прошивку
не трогает, по завершении отправляет останов (`pktcnt = 0`).

Пункт 6 в этой сессии выполнен на неуправляемой нагрузке (лог `docs/stage1/skew-84us.log`): медианный
сдвиг 0 пар, но интерпретация ограничена — фронты «лестницы» сигнала совпадают по U и I сами по себе.
Для окончательного вывода нужна **управляемая ступенька** (ключ + резистор) на стенде пользователя.

## 6. Что требуется от пользователя

Подтверждено пользователем: LED на PA8 мигает (сборка `_my` в приборе), шунт платы = **1 Ом**.

1. **Управляемая нагрузка/генератор** — для min/max на известной нагрузке и ступеньки для оценки
   сдвига U/I (пункты 3.6 и 5.6); пока пользователь нагрузку не подключает.
2. **Источник сигнала на DIO** — пользователь проверит позже; сейчас прибор стабильно читает `DIO = 0xD7`
   (низкие DIO3 = PA14 и DIO5 = PA12) вместо ожидаемых `0xFF` при подтяжках вверх.
3. **Подтверждение пина UART RX** (физически разведён на плате): кандидаты без конфликтов — PA6, PB4, PB20.
4. (Опционально) аппаратная сверка хеша записанного образа, если появится WCH-LinkE:
   `tools/stage1/flash_baseline.sh --check` + `dump_image` (см. `docs/BUILD_NOTES.md`, раздел 7).
